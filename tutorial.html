Pick up where you left off

1

Almost always run in auto mode.

The faster you trust Claude, the faster you get your work done.

Press Shift+Tab to cycle permission modes until it says auto, or start with claude --permission-mode auto.

2

Use Opus 5.5.

Low or medium effort for actual code implementation. High or xhigh for planning, wayfinding and grilling.

/model and /effort change it mid-session.

3

Effort doesn't mean good or bad output.

It only means how much Claude thinks and checks its own work.

If you planned and ticketed well, code needs low or medium. When you're planning and don't quite know yet, higher effort is OK.

4

Use artifacts to understand what's going on.

Ask for a page instead of reading a wall of terminal text. "Publish an artifact comparing X and Y" gets you a page you can skim, keep and share.

5

Play with multimedia.

Claude isn't just text. It reads PDFs and images, and can transcribe what's in them. It works with your files, and draws things: diagrams, SVGs, charts, whole pages.

If it can't do something natively, like generating an image or transcribing audio, it can find or write the right tool for it. So feel free to play.

6

Make Claude write in your voice.

I train my agent on my blog. Write a voice guide from your own writing and point your global CLAUDE.md at it.

7

Think like an automator.

If you're ever doing data entry, ask "can I have Claude do this?"

For anything you're doing, ask yourself: can Claude do this, or can we make a skill for it?

8

Anything you do more than once, make it a skill.

Have Claude write it, using Matt Pocock's writing-for-agents skill.

9

Keep your global ~/.claude/CLAUDE.md short.

It's context for every session you run.

10

Don't let Claude read sensitive info directly.

Have it write a script that reads the secret and puts it where it needs to go, so Claude never sees it.

11

Context is everything.

Every new problem gets a fresh workspace with only the context it needs.

Be as verbose as you like with that context, just don't confuse it - if you're studying bananas, don't mention oranges.

12

Treat Claude like a junior dev.

Give it the exact plan, so it can't fuck up. The more leniency you give it, the more it takes.

13

Claude is a reflection of you and what you know.

It will be sycophantic, so tell it what to do. You're still the driver.

14

Have agents argue.

Have them test things against each other: one builds, another attacks it.

/arena is the extreme version - a whole bracket of them.

15

Trust and verify.

Use test-driven development (/tdd), so the agent can prove the output is correct, not just claim it.

Have Claude run your tests, or audit the code with /ponytail-audit. Matt Pocock's closest is /improve-codebase-architecture.

16

The ticket runbook does most of this for you.

Every ticket works test-first with /tdd, runs the full test suite and gets a ponytail review. Then a separate agent reviews it for bugs, spec and live data. Live data is n/a locally.

The one thing it doesn't do is an audit. Run /ponytail-audit yourself every so often.

17

Don't know what you don't know? Ask Claude.

Keep asking until you get to the bottom of it. That's how you learn to use this.

You no longer have to be a programmer to program.

18

Watch your context.

The statusline's ctx is how much of the window this session is using. Keep it under about 30%.

Past that, /clear or /compact to stay out of the dumb zone.

19

Budget with the statusline.

5h, 7d and pace tell you how much effort and how many parallel sessions you can throw at a problem.

Don't be afraid to work in parallel - just make sure agents working in the same codebase know about each other.

20

Leave system-tui open.

It doubles as caffeine. It keeps your Mac awake while it runs, so you can walk away and leave your agents working.

It uses macOS caffeinate, and only holds the Mac awake while it's open.

21

Name your sessions.

/rename <name>, or start with claude -n <name>, so you can tell which one is doing what.

I name them after their folder or their problem.

22

The starting flow for a small problem.

  1. A new workspace.
  2. /setup-matt-pocock-skills
  3. /grill-with-docs with your plan.
  4. /to-spec
  5. /to-tickets
  6. One subagent per ticket.

Type the skills - Claude can't start them. The main chat never implements: subagents build every ticket, at medium effort (low for a tiny fix). Bigger? /wayfinder first.

What each does: see Plan: get it straight.

23

GitHub is your friend.

Use it to store your work. Claude knows how to organize itself there.

24

Code is cheap.

Don't be afraid to refactor or rebuild something if it's not working. It's often faster to rebuild a system or a script than to fix an old one.

25

Dictate with Wispr Flow.

Download Wispr Flow and talk to Claude instead of typing. It makes your life so much easier.

26

Get excited about working out how to use Claude best.

Treat it as a thought experiment. Being able to take on any problem is fun.

Reading the statusline

Opus·medium │ ctx 64% 128k │ 5h 18% ⟳1h30m │ 7d 30% ⟳4d │ pace +13%

It sits at the bottom of every Claude Code session.

  • Opus·medium is the model and effort.
  • ctx is how full this session's context window is. Keep it under about 30% - past that, /clear or /compact. It only turns yellow at 60%, so don't wait for the color.

Usage and pace

  • 5h is how much of your 5-hour usage window you've used, and when it resets (⟳).
  • 7d is the same, for the weekly window.
  • pace compares your 7-day usage with an even burn. + means you're under it, with room to spend. - means you're over it, so slow down.

system-tui

system-tui

A dashboard for your Mac and your Claude sessions: CPU, memory, disk use by project, network per process, your open sessions and your plan usage. q quits.

Leave it open. It doubles as caffeine: it keeps your Mac awake while it runs, so you can walk away and leave your agents working.

system-tui tips

  • The disk panel scans your code folder. The first scan takes a couple of minutes.
  • Plan usage fills once a Claude Code session is open - the statusline feeds it.
  • Other folder? bash install.sh --code-dir <folder>
  • Not found? Open a new terminal, so it picks up ~/.cargo/bin.

Extra

Arena: make them fight

Hate an answer? /arena hands the exact same task to a crowd of sub-agents, each with a different strategy. They pair off, attack each other's solution, defend and revise, and a judge scores every match. Losers are out, until one solution is left.

By Jake Schincariol: Jakeschincariol/arena-skill, MIT.

Installing arena

The kit installer puts it in for you.

Skipped the installer? Read its SKILL.md first - it's someone else's code. Then paste this into Claude Code:

https://github.com/Jakeschincariol/arena-skill  Install this skill, then confirm /arena works.

Running arena

/arena --quick <task>

--quick starts 16 agents. Each one runs several times as the bracket plays out, so that's about 91 sub-agent calls. The default 100 agents is about 595. This prints the real numbers:

python3 ~/.claude/skills/arena/bracket.py plan --agents 16

Run it in accept-edits or auto mode (Shift+Tab), or you'll approve every file it writes.

It's wasteful. It's also very fun.

Arena burns usage fast - hundreds of sub-agents chewing on one task. Check 5h, 7d and pace on the statusline before you start.

Use --quick for everyday stuff, and save the full 100 for the answer that matters. Then sit back and watch them fight.

Watch the bracket live

Pair it with a living doc, and you get a page that fills in as the tournament runs.

Run /arena --quick on <task> and keep a living doc of the bracket - one ticket per match, synced after every round.

Open the link and watch the rounds close.
